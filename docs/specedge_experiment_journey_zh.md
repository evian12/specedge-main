## 1. 初始复现现象

`4090_jetson` 并没有比服务器自回归更快，甚至明显更慢。

主要原因：

1. Jetson 等边缘设备能力有限，草稿模型生成并不便宜。尤其是 TinyLlama-1.1B，在 Jetson 上单 token / 单层耗时远高于 4090 上目标模型的 decode 耗时。
2. 1 client + 1 server 场景下，4090 没有批处理收益。SpecEdge 的优势更依赖“边端本地推测隐藏云端等待”，但如果云端 4090 本身很快、网络延迟也不大，Jetson 的额外草稿计算会变成负担。


## 2. 草稿模型替换与蒸馏尝试

为降低 Jetson 端成本，尝试使用 AMD-Llama-135M 等更小模型替代 TinyLlama-1.1B。预期是：小模型更快，可以降低草稿开销。

实际问题：

1. 小模型虽然更快，但和 Llama-2-7B-chat 的分布差异更大。
2. 平均接受深度偏短，很多 cycle 只能接受 1 个左右的 draft token。
3. 接受深度短会增加服务端验证轮数，网络等开销会抵消小模型速度优势。
4. 如果使用推测树会导致草稿开销上升。

因此又引入离线蒸馏 / SFT 子项目，希望让小模型输出更像目标模型。蒸馏文档见 `docs/drafter_training_zh.md`。

阶段结论：

1. 短时间内很难稳定把平均接受深度提升到足够高。
2. 在当前实验阶段，蒸馏模型没有稳定超过 TinyLlama-1.1B 的综合表现。

因此后续重新回到 TinyLlama-1.1B 作为 draft model。

## 3. 模拟云端延迟实验

是不是更适合服务器忙碌的场景？
为了让云边推测解码的应用场景更明显，后续加入了模拟 decode 延迟，例如 25/50/100/200 ms。这个延迟模拟的是“云端每步 decode 变慢”或远程服务端响应变慢，而不是简单的一次请求往返延迟。

观察结果：

1. 草稿成本相对变小
2. 延迟越大，SpecEdge 的潜在空间越大，因为客户端在等待服务端验证时可以做更多预计算。
3. 但延迟变大不自动等于加速。只有当预计算结果能命中并被复用时，才会减少后续 cycle 数。
4. 很多慢请求仍然慢，是因为接受深度短、预计算命中率低、或命中后复用深度短。

## 5. 原始 SpecEdge 与预计算问题

原始 SpecEdge 的预计算思想是：服务端验证当前推测树时，客户端利用等待时间从某个候选 root 继续生成后续草稿。如果服务端验证结果刚好落到该 root，则下一轮可以直接复用已经生成好的后续草稿。

早期实验发现预计算在边缘场景没有明显发挥作用，原因主要是：

1. 命中率不够高：服务端真实接受位置不一定等于预计算 root。
2. 复用深度不够长：即使命中，预计算出来的后续 token 数也短。
3. 额外成本偏高：多 root / 多位置预计算会消耗 Jetson 时间，缩短每个 root 能生成的深度。
4. 慢整体进度：当验证结果以及返回，但是预计算还在进行，整体进度会被拖慢。

因此后续优化重点转为：提高命中率、提高复用深度、控制额外 root 成本。

## 6. Deepest Multi 与 Strict 方案

它的主要思想：

1. 初始推测仍然使用树结构。
2. 预计算 root 优先从当前推测树最深叶子中选择。
3. root 数量动态决定，但非常保守。
4. 只有额外 root 的边际收益足够高，才加入第 2/3 个 root。
5. 在线记录 root rank 的命中奖励，如果后续 root 历史收益不够，就 gate 掉。



1. 它没有过度分散 Jetson 计算。
2. 它主要防守最可能全接受的深路径，这和当前 TinyLlama 的接受模式更匹配。
3. 它避免低延迟下因为多 root 导致 proactive 深度变短。
